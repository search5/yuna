# yona → yuna 동치성 회귀 백로그

`yona`(Play/Java)에서 `yuna`(Spring Boot/Kotlin)로 이식하며 발견된 기능 격차를 중요도 순으로 번호를 매겨 정리한 작업 백로그다. 원본 감사 리포트: 이 세션에서 생성한 아티팩트 "요나·유나 동치성 감사" 참고.

## 진행 규칙 (TDD + JaCoCo)

1. 항목마다 **먼저 실패하는 회귀 테스트**를 작성한다 (yona의 기대 동작을 yuna에서 명세).
2. 테스트가 레드 상태임을 확인한 뒤, 최소 구현으로 그린으로 만든다.
3. `./gradlew test`는 `build.gradle.kts`에 설정된 JaCoCo(`jacocoTestReport`)로 `finalizedBy` 연결되어 있어, 테스트를 돌릴 때마다 `build/reports/jacoco/test/jacocoTestReport.xml`(+ html)에 커버리지가 자동 갱신된다.
4. 각 항목을 마치면 아래 표의 상태를 `[x]`로 바꾸고, 관련 커밋/테스트 파일 경로와 커버리지 수치를 "비고"에 남긴다.
5. 번호는 고정 ID다 — 순서가 바뀌어도 번호는 재사용하지 않는다.

상태 기호: `[x]` 완료 · `[~]` 진행중 · `[ ]` 대기

  - **P1-34(Postgres 통합테스트) 먼저 작성**: `DataBackupServicePostgresIntegrationSpec.kt`(신규) — `AbstractIntegrationTest`가 MariaDB 컨테이너에 고정돼 있어 재사용할 수 없으므로, `PostgreSQLContainer` + `@DynamicPropertySource`로 별도의 `@SpringBootTest` 컨텍스트를 새로 구성(스키마는 `test` 프로필의 `ddl-auto: create-drop`로 JPA 엔티티에서 자동 생성 — Postgres에서도 정상 동작함을 이번에 처음 확인). 이 테스트가 실제로 P1-33의 버그를 잡아낸다: 신규 빈 DB에 "PK=1을 이미 점유한" 백업(디저스터 리커버리로 과거 백업을 새 DB에 복원하는 것과 동일한 시나리오)을 `importAll()`로 복원한 뒤, 곧바로 `userRepository.save()`로 신규 유저를 저장 — 수정 전에는 PostgreSQL 시퀀스가 여전히 초기값(1)이라 `nextval()`이 반환한 id=1이 방금 복원된 id=1과 충돌해 `DataIntegrityViolationException`(유니크 제약 위반)이 실제로 발생함을 확인(레드).
  - **P1-33(시퀀스 재설정) 구현**: `importAll()`이 각 테이블 INSERT 직후 `resetAutoIncrement(table, dialect, rows)`를 호출하도록 추가 — 백업된 행들의 `id` 컬럼 최댓값을 계산해, MySQL/MariaDB는 `ALTER TABLE ... AUTO_INCREMENT = max+1`(실측상 이미 자동으로 맞춰지지만 방어적으로 명시 재설정), PostgreSQL은 `pg_get_serial_sequence()`로 실제 시퀀스 이름을 찾은 뒤 `setval(seq, max, true)`로 재설정한다. `id` 컬럼이 없는 조인 테이블 등은 `maxOrNull() == null`이라 자동으로 스킵된다(추가 분기 불필요).
  - 구현 중 실수 하나 발견·수정: `SELECT setval(...)`는 결과 행을 반환하는 함수 호출이라 `jdbcTemplate.update()`(결과 없음을 기대)가 아니라 `queryForObject()`를 써야 했다 — 처음엔 `update()`로 잘못 작성해 "A result was returned when none was expected" 오류가 났고, 이를 고치고 나서야 진짜 그린이 됐다(이 과정 자체가 실제 Postgres로 검증하지 않았다면 못 잡았을 오류라 P1-34를 먼저 처리한 보람이 있었다).
